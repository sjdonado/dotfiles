---
name: open-pr
description: Publish an authorized task branch and open or refresh its PR, completing the requested opened-PR or green-PR outcome.
---

Use existing publication authority for this scope. Mode activation alone grants none. A direct PR request covers necessary commits, push, creation or refresh; it does not authorize review replies, merging, or narrowing the promised behavior. Resolve explicitly undecided behavior before publication. Use existing task state and a temporary gate input, not a separate acceptance document or review ceremony.

1. Inspect the task branch, full index, and complete intended diff. Recover the associated Linear or git-bug human ticket IDs and primary ticket from the original task; do not infer an unrelated ticket merely from the project. Check the shared branch/linkage policy without renaming an existing published branch. Reuse the existing checkout; read worktree when isolation is needed. Never commit to the default branch. Preserve unrelated work. If unrelated files are staged, use `git commit --only -- <intended-paths>` and leave the other index entries intact; if ownership overlaps, resolve it before committing.
2. Complete the delivery stage of principle-prove-it-works against the user's promised behaviors, including deferred checks needed for that scope. For user-facing work, confirm the design checkpoint in principle-preserve-product-experience was satisfied. Reuse valid evidence. Stop before committing, pushing, or opening while a promised behavior is unimplemented or lacks its required evidence, even when all declared CI checks pass. Fix in-scope failures; honor a no-edit instruction. Report the exact blocker without publishing. A draft or prototype label does not waive this gate; only an explicit user scope change can select a smaller deliverable.
3. Read the repository's PR template and standards. Prepare the title and body before creation, following principle-write-for-the-reader. Explain the problem, resulting behavior, actual verification, consequential decisions and alternatives, meaningful risks, and unverified behavior. Add test rationale and suggested reviewer checks when they help assess the change. Keep the summary short and put long evidence in linked artifacts or collapsed details; do not impose a fixed template on another project. Use a fenced Mermaid diagram when supported and it clarifies a flow, state machine, or system relationship faster than prose. Skip decorative diagrams.
4. For every functional change, include `## Demo` or the repository's equivalent section with how to try the promised behavior and its observed result. Use an inspected capture for visible interactions when permitted, or a reproducible command and evidence artifact for a nonvisual contract or when captures are prohibited. An unconnected library cannot demonstrate a promised application journey. If required demonstration is blocked, report the gap and stop publication. For UI captures, read `references/demo.md`. Prose or configuration edits that change no functional behavior may omit a demo with an explicit not-applicable reason in verification; never create decorative screenshots. With gh, pass multiline text through `--body-file` or stdin, never interpolated shell text or literal backslash-n separators.
5. Before publication, run available repository checks for PR titles, body, and metadata at the time the project requires them. Apply the shared ticket rules: use `Resolves <ID>` for completed accepted ticket scope or `Refs <ID>` with remaining scope for a partial/related ticket. Verify labels, applicable checklist items, evidence claims, and attachment paths. Fix in-scope failures before publishing; do not invent a ticket, feature flag, validator, or label requirement. For staged uploads, validate local references now and confirm uploaded references after publication. Never leave a demo placeholder.
6. Stage explicit intended paths and run `scripts/check_delivery.py` against the exact tested source snapshot, following `references/delivery-evidence.md`. Stop on missing, stale, static-only or unverified required behavior evidence or missing demo disposition. Do not erase requirements or relabel checks to make it pass. Inspect the cited commands and artifacts yourself; the checker validates declarations, not their truth. After it passes, commit per principle-write-for-the-reader and push the authorized branch. Create a normal PR, or a draft when requested. Refresh an existing PR in place, preserving human context, issue links, and checked items. Never create a second PR for the same task. Link the URL through the host tool when available, then read back the stored title, body and metadata to confirm formatting, behavior evidence, demo disposition, and usable attachments.
7. Match the requested stopping condition. For opened PR, report its URL and current check state without starting unsolicited monitoring. For green PR or explicit monitoring, complete required remote checks and check mergeability, using the host's event-driven watcher when available. Fix in-scope failures, rerun evidenced flakes once, and resolve mechanical conflicts. Ask only for semantic conflicts or rewriting shared history outside existing authority. Pending checks are not a green result.
8. Report the requested outcome or concrete blocker and anything unverified. Update useful existing task state. Never merge.

If the host owns PR creation, apply the same behavior and evidence gate before handing back title, body and required metadata. Deliver media through supported host attachments or accessible artifact references when available and authorized. A local path unavailable to that host is not a delivered attachment. If required evidence cannot be delivered, return the precise blocked handoff rather than ready-to-publish content. Report unavailable uploads and PR creation as unverified; do not upload to an unrelated service or claim a PR exists from prepared text.
