---
name: worktree
description: Create the worktrunk worktree and branch a new task runs in, named from its Linear issue or by the user, and in T3 Code bind a new thread to it. Use when a workflow starts new work, or for "make a worktree", "create a worktree", "move this to a worktree", "start a branch for this".
---

This block creates the task's worktree; `iteration` and `yolo` call it, and a user can ask for it directly.

1. **Reuse when the task already has a home.** Work on an open PR happens where its branch is checked out: read its branch with `gh pr view <pr> --json headRefName`, and find a worktree holding it with `wt list --format json` (match `branch`, read `path`) or, in T3 Code, the T3 MCP's `t3_worktree_list` queried by branch; prefer these to `git worktree list`, which permissions may deny. When no worktree holds it, run the approvals check from step 5, then `git fetch origin <headRefName>` and `wt switch <headRefName> --no-cd --format json`, and copy that branch's note and task list from the current checkout's `.agent/` into the new worktree, since the pre-start hook drops copied notes. A worktree on a non-default branch with no open PR, created for this task, is reused. Otherwise continue.
2. **Require worktrunk.** If `wt` is not on PATH, stop before editing and say worktrunk is missing. Never create the task's worktree with `git worktree add` or any other tool; disposable worktrees a workflow makes for its own subagents or a bisect, and removes before it returns, are the only exception.
3. **Carry nothing silently.** If the user's checkout holds uncommitted edits that belong to this task, ask how to carry them before creating anything.
4. **Name the branch.** When the task is bound to a Linear issue, use the issue's git branch name exactly, read with the Linear MCP's `get_issue`. Otherwise a branch the user named is used as given. Otherwise propose `<type>/<kebab-summary>` (types as in Conventional Commits) and wait for the user to accept or replace it; inside `yolo`, ask it in yolo's single clarify stop.
5. **Create it.** First run `wt config approvals list`: when it shows an unapproved `pre-start` or `post-switch` command, stop, name the commands, and create nothing until the user approves them (`wt config approvals add`) or says to skip them (`--no-hooks`); unapproved `pre-remove` or alias commands do not block creation. Never pass `--yes`. Resolve the default branch (`git symbolic-ref --short refs/remotes/origin/HEAD`, without the `origin/` prefix), run `git fetch origin <default>`, then `wt switch --create <name> --base origin/<default> --no-cd --format json` and read the worktree path from the JSON's `path`. The `pre-start` hook runs project setup; do not run it again. Then run `rm -rf <path>/.agent`, so no copied branch notes survive whatever the worktrunk config copies.
6. **Bind a T3 thread to it.** Only when the user asked for the worktree directly from a T3 Code thread; a workflow that called this block skips to step 7. Open a new thread on the worktree with the T3 MCP's `t3_thread_launch` and an `existing_worktree` workspace, giving it the PR URL, the route, the branch note's path, and every constraint in force. Never use `t3_worktree_handoff`, which fails on a branch worktrunk already checked out, or Claude Code's `EnterWorktree`, which moves only the agent's shell. Edit nothing further in this thread; step 8's report hands the work over.
7. **Work there.** Unless step 6 handed the work over, every later command runs in that absolute path (`git -C <path>`, or `cd <path>` within the same shell call). Write the branch note and task list in the new worktree per `principle-state-outlives-the-session`.
8. **Report it.** Every final report on work done in a worktree gives its path, how to open it (`cd <path>`, or `wt switch <name>`), and `wt remove <name>` to run once its pull request merges. After step 6, also give the thread as `[title](t3-thread://v1/<threadId>)` and tell the user to continue there, so two threads never edit the same checkout.
