---
name: open-pr
description: Commit, push, and open or refresh a pull request, then drive its checks green. Use from yolo, or directly for "open a PR", "push this and open a pull request", "update the PR".
---

One place for every publication of a task branch. `yolo` calls it; a direct request enters it. Either way the same gates hold.

1. **Gate.** Publish nothing from the default branch; say a task branch is needed (the `worktree` block makes one). Check the agreement per the shared policy's Publication authority: from `yolo`, the run's approval covers its scope; a direct request that names the pull request is the agreement for the branch's current diff, unless the branch note holds an iteration ledger with an open acceptance question: then name that question and ask once before publishing; feedback after a PR is open publishes only the batch the user approved. Anything less: publish nothing and ask once, naming what would be published.
2. **Prove it locally.** Run the local rungs of the ladder through `verification` (`principle-prove-it-works`). Publish nothing while a rung is red. A direct `open-pr` runs no adversarial review; `yolo` already ran one, and a user who wants one asks for `agent-review`.
3. **Commit and push.** Stage explicit files only, never unrelated changes. Commit per `principle-write-for-the-reader`. Push with `git push -u origin HEAD`.
4. **Open or refresh.** With no PR, open a normal PR whose title starts with `WIP:`, unless the user asked for a draft (then use the forge's draft state, no marker). With a PR, mark it `WIP:` while checks run, read its current body first and edit it in place, keeping issue links, closing keywords, checklists and human-written context.
5. **Write the body** per `principle-write-for-the-reader`: problem, resulting behavior, verification with the checks that ran. From `yolo`, also: **Manual verification** (every changed shared unit traced to its other consumers, each affected surface with what to check, or what was searched when there are none), **Assumptions** (decision, rejected alternative, the fact that would flip it), **Refuted evidence** when any, and **Rejected review findings** when any. Include a mermaid diagram where that principle calls for one. Attach screenshots with `gh pr edit <n> --attach '<file>#<alt>'`, never by committing them. Send the body through `--body-file` and read it back.
6. **Drive it green.** Watch required checks to completion; a red required check is a failure to fix, not a result to report (re-run a flake once first). Check `gh pr view --json mergeable,mergeStateStatus`: rebase a conflicting branch, resolve mechanical conflicts, push with `--force-with-lease` on this task branch only, and escalate a semantic conflict. With no remote CI, the resolved checks are the local rungs from step 2 plus mergeability. Do not wait for review threads; `address-review` owns them.
7. **Finish.** Once every resolved check and mergeability are green, remove `WIP:`, including when the repository has no remote CI. Never merge. Report the PR URL, each rung's state, and the worktree per the `worktree` block's report rule. Save the branch note with the PR, checks and next action.
