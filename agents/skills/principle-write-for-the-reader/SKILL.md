Not a workflow: workflows and building blocks read this when a step names it.

**Commit messages.** Conventional Commits, terse and exact, why over what. Subject: `<type>(<scope>): <imperative summary>`, scope optional; types `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `chore`, `build`, `ci`, `style`, `revert`; `!` after the scope marks a breaking change; imperative mood, at most 50 characters where possible and never over 72, no trailing period, capitalization after the colon matching the project. Body only when the why is non-obvious, and always for a breaking change (`BREAKING CHANGE:` line), a security fix, a data migration, or a revert. Bullets use `-`; issue references go last (`Closes #42`). Never: "This commit does X", "I", "we", "now", "currently", restating the file the scope names, AI attribution, filler, or emoji unless the project uses them. This style is for commits only, never for prose.

**Pull request text.** Follow the repository's template or instructions; otherwise sample recent merged PRs from one maintainer and match their structure, tone, length and context. Explain the problem, the resulting behavior and the verification. For an external open source contribution, add a brief thanks when it fits. Include a real screenshot of a runnable UI or TUI change, attached rather than committed. Include a diagram when it explains an interaction or state change faster than prose.

**Messages to anyone other than the user** (issues, PRs, tickets, email, chat, comments). Read the complete thread first. Compare a report's findings with its evidence: state which findings the evidence resolves and request what is missing, never implying the whole report is resolved. Send a body through a file or stdin, never an interpolated shell string; read back what was sent and correct that same message if it is malformed. Ground claims per `principle-evidence-over-assertion`. Write for the recipient: acknowledge useful input when natural, then the finding, evidence, action taken and verification; keep only what helps them understand or act. Mention an adjacent inconsistency only when resolving it prevents confusion or gives them something actionable. Match the platform's conventions and the user's established voice without forcing a template. Reject a suggestion respectfully and specifically, with the alternative and what evidence would change the conclusion. A question asked as the user's agent includes context, what was checked, and the exact decision needed. Never invent the user's beliefs, relationships, authority or intent; never expose internal reasoning, skills or harness mechanics. Nothing here grants permission to send.

**Technical Markdown** (architecture documents, technical README sections). Keep one term per concept, name the actor and action, split sentences that carry several decisions, make references unambiguous. Preserve necessary vocabulary and the repository's voice. Do not claim ASD-STE100 compliance.
