# Design

## Context

See `proposal.md` for motivation and the two delta specs for behavioral requirements.

The current declaration is split across `flake.nix`, Nix home and darwin modules, Nix-packaged upstream binaries, and shell activation fragments. `setup.sh` bootstraps or repairs Nix; `sync.sh` evaluates the declaration to discover packages and accounts, switches the system, and checks the result. Homebrew exists at `/opt/homebrew`, but nix-homebrew owns its launcher and immutable tap links. Configuration links, shell files, per-user defaults, launch agents, and several setup steps are currently generated by home-manager.

The repository previously used `macos.sh`, `linux.sh`, `mise.toml`, and `lib/links.sh`. That implementation is useful evidence for shell behavior, but it cannot be restored wholesale because package choices, shells, applications, agent integrations, and account behavior have changed. The current Nix declaration and `provision-with-nix/coverage.tsv` are the source for the desired state.

The working Mac has multiple accounts. One primary account owns `/opt/homebrew`, `/Applications` items installed by provisioning, and machine-wide settings. Each account has its own checkout at `~/.config/dotfiles`, and its links must resolve into that checkout. Linux targets include Ubuntu containers and Coder-style workspaces on `aarch64` and `x86_64`.

## Goals / Non-Goals

**Goals:**

- Keep one readable shell entry point for setup and one for sync and checks.
- Make package and account declarations inspectable without evaluating code from an external package graph.
- Preserve the present installed command and application coverage unless an item is explicitly dropped during implementation.
- Make every routine step idempotent and every mutation attributable to a named step.
- Keep the candidate reversible until the final, separately authorized Nix uninstall.

**Non-Goals:**

- Exact version reproducibility across fresh machines.
- A universal package abstraction shared by Homebrew and Linux distributions.
- Linuxbrew, a replacement runtime manager, or per-project runtime selection in dotfiles.
- Managing App Store sign-in, tool authentication, environment-secret files, or SSH private keys.
- Restoring obsolete fish, Ghostty, Herdr, Mason, or other pre-Nix choices.

## Decisions

### 1. Keep declarations simple and source-specific

Use these tracked sources of truth:

- `Brewfile`: every macOS tap, formula, and cask, including formulas needed to keep declared cask dependencies during cleanup.
- `packages/linux-apt.txt`: one package name per line for the supported Ubuntu base.
- `lib/installers.sh`: named, guarded installers for commands whose required version or program is not adequately supplied by apt. Each installer detects an already working command, supports both declared architectures or reports an explicit skip, and uses a pinned release when the upstream distribution permits it.
- `lib/links.sh`: common link and generated-user-state primitives shared by both platforms.
- `lib/macos.sh` and `lib/linux.sh`: platform application and check functions.
- `hosts/macos.sh`: the hostname-to-accounts declaration. The first account is the primary account. This is the only tracked file containing real host and account names.

The existing coverage table becomes a migration audit: every current package and command maps to a Brewfile item, apt package, guarded installer, explicit manual item, or deliberate removal. It is not executed at runtime.

Alternative considered: one cross-platform TSV driving both platforms. Rejected because Homebrew already has an executable declaration format, while Linux sources need source-specific installation and architecture handling. A shared abstraction would recreate part of a package manager.

### 2. Homebrew owns all conventional macOS packages

The primary account installs official Homebrew when it is missing, then applies the tracked Brewfile. Normal sync runs with automatic tap updates disabled and converges installed items to the declaration. `sync.sh --upgrade` explicitly updates Homebrew metadata, upgrades declared items, reapplies the Brewfile, and performs cleanup. Cleanup uses `brew bundle cleanup --force`, never `--zap`, and the Brewfile declares cask dependencies that Homebrew otherwise treats as removable.

Fresh setup receives the current versions available from the configured taps. The repository does not claim Nix-style version locks or generation rollback.

Alternative considered: Homebrew on Linux for a common package list. Rejected because Linux still needs distribution packages for system integration, Homebrew has no casks there, and a second user-space prefix would complicate minimal containers.

### 3. Linux uses apt plus explicit installers

The supported Linux implementation is Ubuntu or Debian-compatible and uses apt for system packages and stable tools whose distribution versions are adequate. Commands unavailable or materially incompatible in apt use explicit installers in `lib/installers.sh`. There is no generic runtime manager and no shim directory.

Node, Bun, pnpm, uv, OpenCode, OpenSpec, Worktrunk, and similar non-base tools must each receive an explicit source during the coverage conversion. The implementation may choose a distribution repository, vendor installer, or pinned release archive, but it must record that choice in the installer function and prove both supported architectures in the disposable check before host migration.

Alternative considered: restoring mise only on Linux. Rejected because it would retain the extra state and PATH layer the change is intended to remove.

### 4. Claude Code and Codex remain vendor-managed exceptions

`lib/installers.sh` preserves the current guarded vendor installation for Claude Code and Codex. It installs only when the expected vendor target is absent, leaves installed versions alone during normal sync, and exposes the vendor links through `~/.local/bin` for shells and T3 Code. Upgrade remains owned by each CLI or T3 Code, not `sync.sh --upgrade`.

OpenCode does not share this exception automatically. Its implementation source is selected with the other non-base Linux and macOS tools and must still provide version 2 behavior.

Alternative considered: put every agent CLI in Homebrew or apt. Rejected because Claude Code and Codex self-update integration depends on their vendor installations.

### 5. Separate machine application from per-user application

`setup.sh` and `sync.sh` resolve the macOS host declaration and check the current account before any mutating function. The primary account may run machine application. Any other account is limited to `sync.sh --check` for itself.

Machine application runs once from the primary checkout: Homebrew, cleanup, ownership repair, system defaults, and other shared state. User application runs once per declared account through that account's own checkout and home directory. It installs links, generated user files, per-user defaults, launch agents, keyboard layouts, BrowserRouter registration, application bindings, and agent configuration. The primary process invokes the account's own user entry point with `sudo -H -u <account>` so links resolve into that account's clone.

The primary checkout controls the machine declaration; each account checkout controls that account's linked file contents. Sync reports when account checkouts are on different commits but does not pull or change branches automatically.

Alternative considered: link every account into the primary checkout. Rejected because a secondary account must remain functional when another account or its home is removed.

### 6. Restore shared shell primitives, not the old scripts

`lib/links.sh` is rebuilt from current home-manager destinations and activation behavior. A managed-link helper compares resolved targets, preserves one `.pre-shell` backup for an unmanaged destination, replaces obsolete Nix-generated links, and does nothing to an already correct link. A registry of managed destinations allows checks and stale-link cleanup without duplicating lists.

Generated launch agents are rendered to temporary files, validated with `plutil`, atomically replaced only when changed, and booted out and back in by label. Generated shell blocks use start and end markers and replace their own block rather than append. Independent activation steps run through a wrapper that records failure, continues unrelated steps, and returns failure after all steps finish when required state is incomplete.

Alternative considered: copy the old `lib/links.sh`. Rejected because it contains obsolete destinations and activation integrations and predates the present zsh and multi-account behavior.

### 7. Preserve `setup.sh` and `sync.sh` semantics

`setup.sh` detects the platform, clones the repository on Linux when needed, installs the platform bootstrap, and performs an initial sync. `--macos` and `--linux` force only a matching platform. macOS requires an existing checkout because the host declaration and migration inputs live there.

`sync.sh` supports:

- no flag: apply the current declaration and then check it;
- `--upgrade`: explicitly update package sources and packages, apply, then check;
- `--check`: read-only checks only;
- `--migrate-from-nix`: a separately invoked macOS transition that applies the shell candidate, verifies it, detaches Homebrew and shell state from Nix, verifies again, and only then reaches the Nix uninstall gate.

The migration flag is accepted only for the primary account. It never runs as part of ordinary setup, sync, upgrade, or verification.

### 8. Make host checks independent from the installer

The checks use tracked declaration files and destination registries, not installer success messages. They probe required commands safely, compare Homebrew's top-level formula and cask sets with the Brewfile, resolve every managed link, inspect defaults and launch agents, and start clean login and non-interactive shells. They reject `/nix`, Nix profiles, mise directories, and Linuxbrew in required command paths and shell startup.

`verify/linux.sh` copies the indexed working tree with working-tree contents into a disposable Ubuntu environment, runs setup and host checks twice, and checks both supported architectures. `verify/macos.sh` is non-mutating: syntax checks, Brewfile parsing and item resolution, a throwaway-HOME user application mode, generated plist validation, host declaration parsing, and migration precondition inspection. Behaviors that require host activation remain explicitly unverified until the real host check after application.

Alternative considered: judge shell changes only through static syntax. Rejected because link targets, PATH behavior, installer architecture coverage, and idempotency require execution.

### 9. Treat Nix removal as a staged migration

The implementation first builds and verifies the complete shell path while Nix remains installed. The macOS transition then:

1. Installs or repairs an official Homebrew checkout in the existing prefix without deleting the Cellar, Caskroom, installed applications, or user data.
2. Replaces Nix-store tap links with normal Homebrew-managed taps and verifies `brew`, its repository, its taps, and declared items no longer resolve through `/nix`.
3. Applies shell-managed links, zsh startup, `/bin/zsh` login shells, defaults, launch agents, and per-user state for every declared account.
4. Removes or disables obsolete nix-darwin and home-manager agents and links only after their replacements pass.
5. Runs every host check for every account and records the result.
6. Stops at a clear gate before invoking the installed Nix uninstaller. The actual uninstall is an explicit task with user authorization, never an automatic consequence of a check.
7. After successful uninstall and a final clean-shell check, removes obsolete Nix and mise declarations from the repository.

Until step 6, rollback is the current Nix switch or generation plus the preserved pre-shell backups. After Nix is uninstalled, rollback means reinstalling Nix and switching the retained pre-removal commit; package rollback is otherwise limited by Homebrew and vendor availability.

## Risks / Trade-offs

- [Homebrew and apt do not reproduce exact historical versions] -> Accept moving channels, keep every source explicit, pin release archives where practical, and verify behavior after each sync.
- [A formula or installer may not support both Linux architectures] -> Require disposable checks on both architectures before migration; report unavailable coverage as unverified.
- [Homebrew currently depends on nix-homebrew paths] -> Repair the official checkout and taps in place, prove no `/nix` resolution, and keep Nix installed until that proof passes.
- [Cleanup can remove hand-installed packages] -> Generate the Brewfile from current coverage, compare declared and installed sets before enabling cleanup, and use non-zapping cleanup only.
- [Per-account checkouts can drift] -> Report commit differences and always apply and verify links from the owning account's checkout.
- [Shell scripts can partially apply state] -> Use named idempotent steps, atomic file replacement, independent failure collection, and outcome-based checks.
- [Removing Nix weakens rollback] -> Preserve the working Nix commit and host until the shell candidate passes every gate; require explicit authorization for uninstall.
- [Vendor installers can change remotely] -> Guard installation, avoid reinstalling working tools, pin downloadable releases when available, and treat failed retrieval as a failed setup step.

## Migration Plan

1. Build the package coverage map from the current Nix modules, Homebrew declaration, and existing coverage table. Resolve every item to its new source or an explicit removal.
2. Implement shared link, installer, account, platform, and check primitives without changing the host.
3. Implement the Brewfile and Linux declarations, then pass Linux disposable verification on both architectures.
4. Pass non-mutating macOS verification, including throwaway-HOME idempotency and Homebrew declaration resolution.
5. Apply the shell-managed candidate on the Mac while Nix remains installed, initially without Homebrew cleanup or Nix removal.
6. Compare installed Homebrew state with the Brewfile, resolve every difference, enable non-zapping cleanup, and prove a second sync changes no managed state.
7. Run the explicit migration path to detach Homebrew, shells, links, agents, and every account from Nix. Stop if any account or independence check fails.
8. With explicit user authorization, run the Nix uninstaller, open clean shells for every account, and rerun the complete host checks.
9. Remove the obsolete Nix and mise declarations, update documentation, and rerun Linux, macOS preflight, and host verification.

Rollback before Nix removal uses the existing Nix generation and preserved backups. Rollback after removal requires reinstalling Nix and switching the retained pre-removal commit; therefore the uninstall task is last and separately authorized.
