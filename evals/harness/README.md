# Harness scenario tracking

Declarative regression scenarios run against each harness version and model. The current matrix has 26 scenarios and two providers. Paid runs require explicit authorization; local regression tests and dry runs are free.

## Layout

- `scenarios.json`: scenario source of truth using the existing Promptfoo shape (providers, tests, assertions). Two model entries (`sol-medium`, `luna-medium`) use Pi's `openai` provider, with 26 tests, TypeScript artifact checks and a default latency assertion. Unknown providers and empty selections fail. `vars.branch` seeds an existing task branch, and `vars.continueFrom` names the unique predecessor fixture whose artifacts the fresh session consumes. Historical `openai-codex` runs retain their original provider and command metadata.
- `run.ts`: Bun runner with no packages. Copies fixture artifacts, materializes current repository instructions, seed commits them, creates a local bare remote and live forge substitute, spawns isolated `pi-agent --mode json`, and runs artifact checks. `pi-agent` remains the upstream CLI; `pi` now opens the custom Durable harness.
- `inputs.ts`: copies current `agents/AGENTS.md` and skill trees, appends fixture guidance, and records SHA-256 hashes of these inputs plus the runner, scenario JSON, forge substitute, checks and selected fixture. Obsolete fixture skill copies have been removed; historical run evidence remains intact.
- `checks/*.ts`: artifact assertions shared via `(output, {providerResponse: {metadata: {workingDir, seedHead, workspaceDiff}}})`. Git commit and remote heads, the forge operation log, and posted issue bodies determine publication and closure. Final prose names the unresolved caching decision, checkout location and feedback checkpoint.
- Bounded work requires a successful `yolo` read, committed and clean `label.py`, validation execution, a matching pushed head before PR creation, and a checkout report naming the fixture path or branch or identifying the current repository worktree unambiguously. Mixed scope requires a successful `proto` read, local validation, unchanged branches and no observed publication command. Recoverable work requires grounded rationale, an ignored updated note, validation, no publication, and a stop or acceptance question backed by the saved feedback state. Open-shape checks require a runnable slice and local state, not unstated casing or blank-input decisions; transcript review judges whether the proposed behavior fits the user's open request.

## Commands

Free, run anytime:

```
bun run.ts --list
bun run.ts --dry-run
bun run.ts --dry-run --filter-pattern recoverable
bun test *.test.ts
python3 -m json.tool scenarios.json >/dev/null
bun build checks/*.ts --outdir /tmp/tscheck-build && rm -rf /tmp/tscheck-build
```

Paid, only when explicitly authorized (recoverable smoke is 2 sessions, the full matrix is 52):

```
bun run.ts --run --filter-pattern recoverable
bun run.ts --run
```

Each `--run` invocation creates a unique ignored `results-*` directory. Every attempt retains its final fixture repository and bare remote, exact prompt, input hashes, Pi version and full command, isolated settings description, transcript, stderr, result, and aggregate results. Execution uses a temporary repository outside this checkout to avoid inheriting its project instructions; the final repository snapshot is copied into the attempt directory. A started result records the execution path before setup so interruptions remain visible, including the temporary repository when a process is interrupted before the snapshot. Setup failures retain their diagnostics. Earlier root-level transcripts remain historical evidence.

Selecting a continuation automatically includes its predecessors for the same provider. The handoff round-two session copies the accepted round-one repository, including uncommitted implementation, ignored note, and rationale, rather than using the independent round-two fixture as a substitute. Its result records the predecessor attempt and hashes. A missing or failed predecessor blocks paid continuation. Dry runs carry predecessor seed snapshots for wiring only; their assertion negatives do not establish acceptance. Feedback scenarios start on the PR's existing `proto/handoff` branch, with `main` retained as the base. Checkers derive note paths from the seeded branch.

Pi fixture processes do not inherit `HERDR_ENV`: they run outside Herdr and their failing Herdr stub must not advertise a real workspace. This makes the workspace-requested scenario's in-place fallback match the seeded premise. Host environment state remains unchanged.

The runner exits nonzero on any assertion failure, setup error or provider error. A final Pi `error` or `aborted` message fails even when the process exits zero. A transient error followed by a complete successful turn stays visible in `providerErrors`. Incomplete or malformed transcripts fail. `skill-used` requires a successful completed native `read` call for the named `SKILL.md`; mentions in the prompt or output do not count. Unsupported assertions fail. Default assertions are merged with each scenario's assertions. Dry runs report seed-state negatives and unknown latency without calling Pi.

Validation evidence comes from successful completed native Bash calls that run the fixture's `check.py` or Python assertions exercising `label`. The validation checker accepts direct commands and simple successful `&&` chains, including the safe `PYTHONDONTWRITEBYTECODE=1` prefix and literal Python string escapes in double-quoted shell arguments. It rejects ambiguous shell wrappers, control flow, pipes, redirects, substitutions, adjacent quoted fragments, skipped commands, and masked exit status. Assertions may be inline, in a terminal heredoc, or in the exact executed Python file whose resolved path stays inside the fixture; optimized Python, files reached through symlinks outside the fixture, and secret-named paths are rejected. A bounded stdlib AST guard recognizes label-related assertions in straight-line code, literal nonempty case loops, and zero-argument test functions that are actually called, including main guards. Comments, uncalled functions, early exits, short circuits, rebinding, and unsupported control flow fail closed. The guard parses candidate source without executing it; it recognizes evidence shape, not assertion correctness or general Python semantics. A marker file or quoted command mention is insufficient. The shared Oracle rule requires checks to preserve their own status in a separate call instead of guessing the status of a command followed by Git housekeeping. The separate publication check remains broader and catches direct Git operations, shell wrappers, and publication followed by resets or branch deletion. Arbitrary script indirection remains a transcript-review concern. External reply checks require repository citations, resolved dependency facts, allowed dash prose, an actionable mismatch between the four-item title and the single documented dependency, ordered forge operations and unchanged tracked code. A narrow attribution check rejects unqualified canned test claims in both the posted reply and final output, but permits an explicit immediate correction of quoted `check.py` output. Transcript review still judges the meaning of these statements; the external `check.py` prints test claims and does not run those tests.

The default communication assertion checks the local forge substitute's supported message writes. PR creation, issue replies, and body edits must use `--body-file`, including `-` for stdin; inline bodies fail even when subsequently corrected. Read-only calls and title-only edits require no body. This does not interpret arbitrary external APIs or replace recipient-facing semantic review.

## Native code mode

Both Pi eval paths explicitly load `builtin:codemode` and `builtin:mcp` despite `--no-extensions`. The isolated agent directory receives only managed `defaultTools: ["+codemode"]`, `codemode.mode: "on"` and an empty `mcp.json`. Native read, Bash, edit and write tools remain direct. Do not replace this selection with Pi 1.0.2's CLI `--tools` allowlist: it prevents later-registering MCP tools from becoming callable inside code mode. No live browser, simulator, git-bug or personal-account server is connected by the eval runner. Results record effective settings, the complete command and the managed settings hash. Earlier evidence remains historical, not acceptance of later runner or configuration changes.

The session receives the Reviewer B role and a small supplied diff that replaces whitespace normalization with a single-use configurable pipeline. It rejects explicit casing changes and new fallback values but does not demand redundant prose keywords for behavior already preserved by that expression. Seed hashes, Git state, ignored new files, forge logs and observed publication commands must show no writes or publication. Transcript review must still judge case, whitespace, blank inputs, error behavior, transient writes, and hidden script effects; the narrow language guard is not a semantic proof. This probes the reviewer role directly, not orchestration or subagent dispatch.

The explicit Ponytail request in phase-continuation round two still requires `skill-used: ponytail`. Run the same filter with `--dry-run` before an authorized `--run`; local checker tests and seed-state results are wiring evidence only.

Transcript review verifies that both skill reads and the complete thread read precede the code repair. Push, reply, resolve and PR-edit attempts fail acceptance. The fixture declares no remote CI, so a separate remote-check command is not required. This is a local repair probe, not acceptance of authorized external publication. Standalone verification activation remains untested; a verification read inside a selected implementation transcript is covered by that session's skill-unused assertion.

## Managed preview capability limit

The current runner enables Pi's native Bash and code mode, with no external extensions or MCP servers beyond the built-ins. Installed Pi 1.1.0's Bash schema accepts only `command` and `timeout`; execution waits for the child process to finish and returns output, exit code and elapsed time, not a managed background-shell ID. Its internal detached process-group tracking is cleanup machinery, not a model-facing background registration capability. This runner cannot test OpenCode's `shell` with `background: true` or verify a preview left registered at handoff. Do not add a fake registration marker or detach a server to pass a Pi scenario. The smallest truthful behavioral check is a disposable OpenCode session with the native shell tool: retain the prompt and transcript, confirm a background shell registration and HTTP readiness, observe the server still registered at feedback handoff, then stop that specific shell during cleanup. Pi can test reporting the capability blocker, but that is not acceptance of managed preview execution.

`native-preview.ts` provides that opt-in smoke for installed OpenCode 2.0.26. Run `bun evals/harness/native-preview.ts --dry-run --model=gpt-6.1-sol` first, then its authorized `--run` counterpart; repeat with `gpt-6-luna`. Each invocation records current instructions/skills, input hashes, exact command and version, native JSON tool events, model usage when available, and pre-cleanup registry/HTTP evidence under ignored `results-native-preview-*`. It uses the shared service so the managed shell can survive the model client's return, disables configured MCP servers and external plugins only in its disposable project, and refuses JSONC isolation it cannot inspect safely. It neither changes global config nor restarts the service. The model must launch with `shell.background: true`, receive a registered running shell ID, complete an HTTP readiness check through shell or Code Mode before feedback handoff, and leave the shell running. The runner independently checks registration and HTTP readiness after client return, then removes only shells matching its unique fixture/session and verifies their absence. Transcript review remains required for equivalent checks the event assertions do not recognize. This smoke is not a provider benchmark or proof of long-context acceptance.

## Reading results

Pass rate per model first, then token usage medians among passing runs with known usage only. Report unknown usage separately. Never pool models or scenarios, and compare costs only when recorded by the provider. A provider error (auth, model access) is reported distinctly from an assertion failure so access gaps never read as harness regressions. This slice tracks missing PR creation after push (`route-bounded`), missing local check execution (`external`), ungrounded reply facts, publication from mixed scope, and recovery of the earlier prototype rationale. Transcript review remains required before behavioral acceptance.

## Coverage retirement decision

Keep the overlapping Python cases. This four-scenario slice does not establish parity with the larger matrix, and the retained legacy regression contains both task failures and matcher disagreements. The user approved publishing the eval tooling with those failures documented, not treating the behavioral gate as green. Historical batches remain ignored local evidence. Retire a Python row only after repeated runs with the same prompts and model settings establish equivalent artifact and transcript coverage. No token savings or general harness acceptance is claimed by this migration.
